# MarkReview Product Requirements

## 产品定位

MarkReview 是一个面向 Markdown 写作和 AI 协作修改的 VS Code 插件。它帮助用户在 Markdown 原文中快速添加批注和修订建议，让同一个 `.md` 文件既能被人阅读和编辑，也能直接交给 Codex 或其他 AI 处理。

MarkReview 第一版追求小而可用：围绕选中文本插入 CriticMarkup 标记，提供基础可视化，并支持导出 AI 提示词。它不做复杂文档管理、多人协作平台或外部批注数据库。

## 产品目标

- 让 Markdown 用户可以像使用 Word 批注一样快速标记问题和修改建议。
- 保持批注、修订和正文在同一个 Markdown 文件中，降低用户与 AI 协作的沟通成本。
- 让 Codex 能直接读取带 CriticMarkup 的 Markdown，并根据批注输出干净 Markdown。
- 第一版只覆盖最核心的写作审阅闭环，不引入复杂状态管理。

## 核心产品判断

### 采用 CriticMarkup 单文件方案

第一版使用 CriticMarkup 作为批注和修订的主存储格式，并直接写入 Markdown 原文。

选择该方案的原因：

- 用户只需要管理一个 Markdown 文件。
- 用户可以直接把原文交给 Codex，不需要解释额外批注文件在哪里。
- Agent 不需要额外读取外部状态文件，使用门槛更低。
- 批注内容和上下文天然共处于同一文本中，方便 AI 理解。
- 文件即状态，适合本地写作和轻量 AI 协作。

### 第一版不使用 JSON 作为批注主存储

第一版不要把批注保存在单独 JSON 文件中。

不选择 JSON 主存储的原因：

- 用户和 Agent 的沟通会变复杂，需要同时传递 Markdown 和 JSON。
- 用户可能不知道批注 JSON 存放在哪里，或忘记同步对应文件。
- Agent 需要额外读取和关联外部文件，增加处理步骤。
- JSON 批注模型更接近文档管理系统，不符合第一版“小而可用”的定位。
- 外部状态容易造成正文、批注和上下文脱节。

说明：VS Code 插件自身的配置或项目元数据可以使用必要的 JSON 文件，但第一版批注主存储不能是外置 JSON。

### 第一版暂不使用 Comments API

第一版优先使用编辑器 decorations 对 CriticMarkup 进行可视化，而不是使用 VS Code Comments API。

原因：

- Comments API 更适合外置批注模型。
- 外置批注通常需要 JSON 或其他状态存储。
- 这会削弱“单个 Markdown 文件即可交给 AI”的核心体验。
- 后续可以探索 Comments API + CriticMarkup 的混合显示，但不作为第一版目标。

## CriticMarkup 规则

| 标记 | 含义 |
| --- | --- |
| `{++新增内容++}` | 新增内容 |
| `{--删除内容--}` | 删除内容 |
| `{~~旧内容~>新内容~~}` | 替换建议 |
| `{==被标记内容==}` | 高亮或选中的待处理内容 |
| `{>>批注意见<<}` | 批注 |

批注场景中，第一版使用组合标记：

```markdown
{==选中文本==}{>>批注意见<<}
```

## 核心命令与验收标准

| 命令 | 用户输入 | 插入结果 | 验收标准 |
| --- | --- | --- | --- |
| `MarkReview: Add Comment` | 选中文本，输入批注意见 | `{==选中文本==}{>>批注意见<<}` | Markdown 编辑器中选区被正确替换；原选中文本和批注意见完整保留；未选中文本时给出明确提示。 |
| `MarkReview: Replace Suggestion` | 选中文本，输入替换建议 | `{~~选中文本~>替换建议~~}` | 选区被替换建议包裹；替换建议为空时不写入无效标记。 |
| `MarkReview: Delete` | 选中文本 | `{--选中文本--}` | 选区被删除标记包裹；未选中文本时不修改文档。 |
| `MarkReview: Add Text` | 光标位置，输入新增内容 | `{++新增内容++}` | 新增标记插入到当前光标位置；输入为空时不修改文档。 |
| `MarkReview: Clean / Accept Changes` | 当前 Markdown 文档 | 干净 Markdown | 保留新增内容；删除删除标记内容；使用替换建议的新内容；对批注标记给出第一版明确处理策略。 |
| `MarkReview: Export AI Prompt` | 当前 Markdown 文档或当前编辑上下文 | AI 提示词 | 生成包含 CriticMarkup 规则、处理要求和输出要求的稳定提示词。 |

## Clean / Accept Changes 第一版策略

可自动处理的标记：

- `{++新增内容++}` 转换为 `新增内容`。
- `{--删除内容--}` 直接移除。
- `{~~旧内容~>新内容~~}` 转换为 `新内容`。

需要谨慎处理的标记：

- `{==内容==}{>>意见<<}` 代表自然语言批注，第一版不强行自动改写。
- 可选策略一：移除批注标记，保留被标记内容。
- 可选策略二：提示用户该类批注需要 AI 处理。

第一版应优先采用可解释、低风险策略，避免在本地插件中自行猜测复杂改写结果。

## 可视化验收标准

第一版可视化目标包括 editor decorations 和 MarkReview 自定义预览。Decorations 用于源码编辑器内的轻量提示，自定义预览用于完整阅读带 CriticMarkup 的 Markdown。

Decorations 目标：

- `{==内容==}` 显示为高亮。
- `{>>批注<<}` 显示为批注样式。
- `{--删除--}` 显示删除线。
- `{++新增++}` 显示绿色新增样式。
- `{~~旧~>新~~}` 显示为替换建议样式。

可视化只增强阅读体验，不改变 CriticMarkup 作为主存储的事实。

## 非目标

- 不实现复杂文档管理系统。
- 不引入 GitHub PR 工作流。
- 不把外置 JSON 作为第一版批注主存储。
- 不要求用户维护 Markdown 与批注文件之间的映射关系。
- 不在第一版构建多人协作、权限、审阅状态流转等重功能。

## 待细化问题

- `Clean / Accept Changes` 对 `{==内容==}{>>意见<<}` 的默认策略最终选用“保留内容并移除批注”还是“提示需要 AI 处理”。
- 多个重叠或嵌套 CriticMarkup 标记是否在第一版明确禁止。
- 标记出现在代码块中时，命令和清理功能是否应跳过或提示用户确认。
